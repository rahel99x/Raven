# Raven adversarial review: bugs and performance

Oct 20, 2026 · @Alex

## Verdict

Raven at `b98742f` is not ready for more users on a shared cluster. This review found 170 problems, 12 of them critical, and reproduced every critical one:

- A script with an empty variable cancels a job Raven picked for it (MUT-1), and editing the pending part of an array kills its running tasks (MUT-2).
- A rank-dependent first call makes a distributed job hang, or corrupts the application's own all-reduce (INP-1).
- Raven's Cancel SIGKILLs `salloc`, so the queued request it meant to withdraw survives and can run, billed, with nobody attached (HV-3).
- With the default empty cluster id, one interrupted or rejected Heavy request blocks every later Heavy start until someone deletes a receipt by hand (HV-1, HV-2, HV-4) — the exact errors from the CARC launch.
- Recordings of jobs not under the cursor are never read again, and one short write stops a recording until someone repairs it by hand (DATA-1, DATA-2).
- With 22 or more jobs on Slurm 23.02+, the job view is empty (COL-1); after a shell handoff Raven ignores every key and cannot be quit (UI-1); under umask 002 an update cannot succeed and leaves the checkout moved (INS-1).

The code is careful at the level of a system call — argv lists, validated values, no-follow exclusive writes, fsync, atomic renames — and careless about what the user meant and what a cluster is like. Seven patterns produce most of the 170:

1. **Raven guesses the target of destructive actions.** The first row, the whole array, string-ordered ids, a replayed SubmitLine (MUT-1, MUT-2, MUT-3, MUT-5).
2. **Every budget is a cliff.** Line-counted JSON (COL-1), 256 MiB of state (DATA-4), 32 MiB of telemetry (DATA-5), 2,048 gaps (DATA-6), a 5 s export deadline (DATA-7), a 1 MiB trace index (INP-9), 1,024 tasks per session (HV-10), admission slots that leak (HV-8), structure limits that disagree (HV-9), bytes charged on request instead of on read (COL-3). Each fails permanently instead of degrading, and none is tested at its default.
3. **Uncertainty is a dead end.** Raven is right never to treat silence as proof, but it never collects the proof it would accept. Receipts never reconcile (HV-1, HV-2, HV-4, HV-5, HV-6, HV-13), a torn tail blocks every later append (DATA-2), and an update moves the checkout and then can neither finish nor revert (INS-1, INS-13).
4. **Processes are stopped the wrong way.** SIGKILL where a hang-up was needed (HV-3, HV-11, INS-6), and only the shell killed where the whole group should go (LOG-5, MUT-4).
5. **Code inside user jobs trusts cached state and inherited locks.** Rank, helper status and client presence freeze at the first call (INP-1, INP-6, INP-19), and locks and threads cross fork (INP-4, INP-5, INP-10, INP-26).
6. **The trust model was written for a laptop.** No group write anywhere, no symlinked ancestor, every ancestor owned by the user or root (T-2, INS-1, INS-2, INS-3, LOG-8, INP-24). CARC has umask 002 with private groups, PI-owned project directories, symlinked scratch and NFS homes; the rules reject all four, and Raven's own installer writes files its readers then refuse.
7. **Tests agree with the code instead of the world.** The fake `scontrol` accepts comma lists the real one rejects (MUT-7), a test asserts the reader pop behind UI-1, the recovery fixture uses an integral timestamp no real receipt has (HV-2), retention tests override the default gap (DATA-6), and no CI job runs under umask 002 or without `$USER`. The 18,680 passing tests catch none of the twelve critical findings.

A UI thread that still does I/O (UI-2, UI-7, UI-8, LOG-2) and an import graph that is one large hidden cycle (S-1) make each of these harder to fix.

Stop adding features until PRs 1–6 of the fix plan land. Each is small or medium. Together they remove every way Raven destroys work, harms a running job or traps a user, and they clear the Heavy lockout CARC users hit today. PRs 7–13 make Raven dependable on a shared cluster; PRs 14–17 are the performance and structure work.

## Scope and method

The review covers `main` at `b98742f` (2026-10-18), which is what `install.sh` installs today. History was force-pushed since the first review at `33316a0` (2026-10-17), so the comparison is tree to tree.

| --- | --- | --- |
| `raven/` | +18,484 / −705 lines in 149 files (64 new modules, 85 modified) | 332 modules, 126,469 lines |
| `tests/` | +65,950 lines in 694 files | 462 files, 125,599 lines |
| `docs/` | +334,569 lines in 910 files, mostly raw CI evidence | 27 MB, 22 MB of it under `docs/implementation/` |
| `examples/`, `scripts/` | +7,594 lines in 84 files | trace labs, Slurm container, qualification scripts |

Method:

- **Nine independent reviewers**, one per area (UI loop; Slurm collection; Heavy allocation lifecycle; data and evidence; code that runs inside user jobs; installer and updates; analysis and services; logs, terminal and hooks; scheduler mutations). Each was told to assume nothing works and to prove every finding with a reproduction or a measurement.
- **Static analysis** of the whole package: pyflakes, ruff with bug, security and performance rule sets, and an AST pass for function size, function-level imports and import cycles.
- **The full test suite**, run in parallel with timing.

Every finding is labeled **VERIFIED** (reproduced or measured here) or **CODE-READ** (traced end to end without running). Anything that could not be confirmed was dropped. Every critical finding, and several high ones, was then reproduced or re-traced a second time by the lead reviewer; those are marked as re-run or re-checked independently. The container has no `ssh` binary, no Slurm controller and two CPUs, so SSH- and Slurm-dependent paths were exercised through Raven's own fake backends and simulator, and through purpose-built fakes of sbatch, scancel, scontrol, squeue, sacct, salloc and srun that log every argument and signal and follow Slurm's source and man pages.

## UI loop, rendering and input

The new wakeup channel and synchronized output are correct, but the loop around them is still a 200 ms poll that rebuilds whole documents, the UI thread still runs Slurm commands and fsyncs, and one handoff path can lock the user out of their own terminal.

**UI-1 · Critical · VERIFIED (re-run independently) · `raven/screen.py:2011-2013`, `:743-760`, `:898-920`.** After the allocation-shell handoff, `_operation_terminal` pops the bound input reader. `_read_input` then creates a bare reader with no `input_owner` or `geometry_owner` (`_bind_input` runs once, at startup), so every later event has `origin=None`, and `_apply_input` discards origin-less events whenever an embedded terminal has focus. From then on every key, paste, click and Ctrl-C is dropped silently: focus cannot leave the shell and Raven cannot be quit, because curses is in raw mode and Ctrl-C never becomes SIGINT. Reproduction: before the handoff `[('s', {'type': 'key', 'key': 'q'})]`; after it `[]`. The existing test `test_ops_ui::test_terminal_handoff_restores_input_after_all_child_outcomes` asserts the pop, so the suite protects the bug. Fix: rebind after the handoff (`reader = _bind_input(stdscr, app); reader.control_response = app.terminal_sync.receive`) or reset only the parse state, and add a test that types into a focused shell after a handoff.

**UI-2 · High · VERIFIED · `raven/controller.py:2325`, `:2287`, `:2226-2250`; `actions.py:40-55`; `slurm.py:1603-1616`, `:1714-1727`.** Confirming cancel, hold, release, requeue, top or chain runs `scancel`/`scontrol` on the UI thread (15 s timeout), and `:resubmit` runs `sacct`, `scontrol`, `sbatch --test-only` and then `sbatch` there too. With a 3 s controller: `confirm 'y' -> handle() returned after 3.01 s; scancel ran on thread 'MainThread'`; resubmit blocked 3.0 s, then 1.0 s more on confirm. Over SSH to a busy slurmctld the screen freezes for seconds. Fix: validate on the UI thread, run on a worker lane the way `finish_confirm` already runs `submit`, show a pending state and publish the result from the completion callback.

**UI-3 · High · VERIFIED · `raven/screen.py:1944-1960`, `:2006-2010`.** The pager handoff runs `subprocess.call(less …)` in Raven's foreground process group with the default SIGINT handler. Ctrl-C is how you leave `less` follow mode, and it raises KeyboardInterrupt in Raven, which SIGKILLs `less` and exits Raven: in a pty, `{"loop_alive_at_10s": false, "run_curses_raised": "KeyboardInterrupt"}`. The two handoff paths have drifted: this one leaves bracketed paste enabled, the other treats Ctrl-C as "child killed". Fix: one shared handoff helper that disables mouse and paste reporting, installs a no-op Python SIGINT/SIGQUIT handler while the child runs (exec resets it, so the child still gets Ctrl-C), catches KeyboardInterrupt, flushes input, restores modes and rebinds the reader (UI-1).

**UI-4 · High · VERIFIED · `raven/screen.py:2049-2057`, `:2074-2083`, `:1826-1836`; `layout.py:375-396`; `slurm.py:613`, `:643`.** Scheduler text is never sanitized before drawing — including other users' job names on the group tab (`squeue -A`). In `--once`/`--watch`, `L.to_text` writes ESC and OSC sequences straight to the terminal: a job named `x\x1b]52;c;ZWNobyBoaQ==\x07y` produced `raw ESC in --once output: True | OSC52: True` — a labmate can write your clipboard or retitle your terminal. In curses, `\b` and `\t` move the cursor, so `RUNNING  x\b…\bFAILED` leaves `FAILED` on screen, and `vlen` disagrees with what is drawn. Fix: escape C0/C1/format characters once, at the paint and `to_text` boundary (plus the parsers' display fields), and make `vlen` match.

**UI-5 · High · VERIFIED · `raven/screen.py:1551-1573`, `:1614-1631`, `:1701-1705`, `:1472-1522`; `job_row_cache.py:81-117`.** `wait_ms` still caps every wait at 200 ms and maintenance runs five times a second. Only the managed Jobs page has a publication token; every other page rebuilds the full document at each 200 ms boundary, and a rebuild of an unchanged store is O(jobs) because the row "cache" key hashes every field of every job. Measured idle, real loop, 10 s windows: Jobs at 5,000 jobs 9.5% of a core; Jobs with the analytics panel at 5,000 jobs 27.3%; History at 5,000 rows 17.4%. Real publications caused only 0.2–1.0 wakeups/s of the 4–6.5 measured. Fix: rebuild on revision counters, not field scans; make published records immutable (`apply_starts` mutates `Job` objects in place); give every page a token and drop the fixed tick; patch clock cells once a second instead of recomposing.

**UI-6 · High · VERIFIED · `raven/job_row_cache.py:114`.** The prepared-row cache key includes `selected_id` and `frozenset(marks)`, but prepared rows depend on neither (`rows identical across selection: True | keys equal: False`), so every cursor move or mark re-prepares every row: one Down-arrow frame costs 27.8 ms at 1,000 jobs and **202 ms** (126–260) at 5,000. Fix: drop both from the key — selection styling is applied after the cache — and test that a cursor move is a cache hit.

**UI-7 · High · VERIFIED · `raven/controller.py:296-299`, `:619-632`, `:696`, `:834`, `:1185`; `model.py:1294-1307`; `screen.py:2042`.** Key handling still calls the full `Store.snapshot()`, which copies every CPU and GPU history under the Store lock and blocks the sampler meanwhile. On History, one arrow key calls it three times and re-sorts the whole history each time: **410 ms median per Down key** at 5,000 rows with 600-point histories (`snapshot()` 141 ms versus `render_snapshot()` 4.2 ms). `run_watch` calls it every interval too. Fix: use `render_snapshot()` or the frame's cached snapshot on UI paths, cache `history_jobs()` by (revision, view options), and switch `run_watch`.

**UI-8 · High · VERIFIED · `raven/model.py:611-693`, `:705-715`, `:1077-1078`; `ui_state.py:89-107`; `controller.py:605-611`, `:1707-1709`; `raven_limits.py:251-318`.** Tags, pins and notes are saved synchronously on the UI thread, once per job, each save re-serializing all tags with two fsyncs and a rename. Tagging 100 marked jobs with 2,000 already annotated took 442 ms (200 fsyncs); at 20 ms per fsync, typical of an NFS home, the UI froze for **4.68 s**. `Store.event()` also appends `events.jsonl` on the UI thread (41 ms median with a concurrent series writer). Fix: update memory under the lock, then hand persistence to a coalescing writer lane (the `UIWriter` pattern already used for `ui.json`), and make tag/pin bulk operations one write.

**UI-9 · Medium · VERIFIED · `raven/clipboard.py:62-73`.** `y` and the row/selection copy commands call `clipboard.copy` on the UI thread, which tries each clipboard tool with a 5 s timeout: with a stale `DISPLAY` under `ssh -X`, one copy froze the UI for 10.0 s. Fix: keep the file export and OSC 52 inline; deliver to tools on a worker lane with one overall deadline.

**UI-10 · Medium · VERIFIED · `raven/screen.py:1910-1913`; `model.py:513`.** The bell counts `started` events in the bounded 200-event window; once it is full the count stops rising and the bell never rings again (5 of 5 starts rang before the window filled, 0 of 10 after). Fix: ring on a monotonic `started_seq`.

**UI-11 · Medium · VERIFIED · `raven/model.py:1010-1012`, `:830-844`.** `_recording_identities`, `_recording_observations` and `_recording_evidence` gain an entry for every job id ever seen and are never pruned: cycling 40,000 array-task ids with 1,000 live left 40,000 entries and 24 MB of heap. A week-long session on a busy account leaks steadily. Fix: prune them in `apply_jobs` against retained attempts, series and finished ids.

**UI-12 · Low · VERIFIED · `raven/ui_wakeup.py:129-132`; `screen.py:1701-1705`.** Resize never wakes the loop (`select` retries after signals since Python 3.5, so the `InterruptedError` branch is dead); resizes are noticed only at the next 200 ms poll (median 102 ms, `signal_wakeups: 0`), which is part of why the poll cap cannot be removed. Fix: a SIGWINCH handler that writes to `signal.set_wakeup_fd` — not `UIWakeup.notify()`, whose lock deadlocks if the signal lands inside `drain()`.

**UI-13 · Low · VERIFIED · `raven/controller.py:605-611`.** Pinning several marked jobs toggles each one separately: with job 1 pinned and job 2 not, the result is `{'1': False, '2': True}` and the message says "unpinned 1, 2". Fix: decide once (`target = not all(pinned)`) and apply it to all.

**UI-14 · Low · VERIFIED · `raven/historical_replay.py:29-56`; `historical_ui.py:116-127`.** With `:asof record on`, every 2 s capture serializes up to 2,000 jobs, 2,000 history rows and 10,000 samples while holding the Store lock (58 ms at 5,000 jobs; concurrent `render_snapshot()` waits 42 ms median). Fix: copy references under the lock and serialize outside it.

Held up under review: `UIWakeup` (one pending byte, race-free notify/drain/close, consistent lock order, non-inheritable fds); synchronized-output begin/end stay balanced through exceptions, nested frames and write failures and never span an input wait; rebuilds use `render_snapshot()`; hover feedback costs under 1.5 ms at 5,000 jobs; `ui.json` saves go through `UIWriter`.

## Collection, Slurm parsing and the sampler

The earlier parsing bugs are fixed and the JSON normalizers handle every recorded Slurm shape, but the governed collection layer wraps them in budgets that real output exceeds: on any modern Slurm, a user with 22 or more jobs sees an empty Jobs view, and the warning the CARC user saw freezes finished jobs on screen as RUNNING.

**COL-1 · Critical · VERIFIED (re-run independently) · `raven/slurm.py:1104-1131` (re-raise at `:1110-1113`); `platform_session.py:128-129`, `:140-141`; `raven_collection.py:36`; `slurm_json.py:27-28`, `:57-58`, `:75-79`.** Every installed launcher runs in managed mode, and on Slurm 23.02+ (whose `--help` advertises `--json`) Raven asks for `squeue --json` / `sacct --json` first. Slurm pretty-prints that output — about 470 lines per squeue job and 520 per sacct job — and the governed owner counts output **lines** against a 10,000-"record" budget and a 4 MiB cap, so the read raises. `_json_read` re-raises every JSON failure except "unrecognized option", never caches JSON as unusable, and never tries the text reader — even on versions whose document it would discard as unqualified anyway. Reproduction on 24.11.7 fixtures: 21 jobs → `store.jobs=21`; **25 jobs → `store.jobs=0 error='Governed collection: Scheduler read exceeded the site record budget' backoff=30.0s`**. 26.05.5 behaves the same; 20 sacct jobs fail History the same way; a crashing `squeue --json` (24.05.1 aborts with `malloc(): invalid size`), a timeout, or one control character in one job's comment take the same path. Impact: anyone with 22+ jobs (one 25-task array), \~20 jobs in the 48 h history window, or a lab account over 21 jobs gets an empty view plus an error every cycle. Fix: learn the parser cheaply before fetching jobs (`--json=v0.0.45` fails fast on older installs, or use `squeue --version`); in `auto` mode treat any JSON command or document failure as "JSON unavailable", run the text reader for this poll and cache the negative result; budget JSON by job count and bytes, not lines; validate strings per record.

**COL-2 · High · VERIFIED (re-run independently) · `raven/sampler.py:717-720`, `:1035-1038`, `:1066-1069`, `:557-561`; `slurm.py:1133-1134`, `:607-611`, `:637-640`.** Whenever a parse is marked partial — JSON `warnings` even with zero rows, an "ambiguous" optional column with every row accepted (a `|` in one job comment), or one rejected row — the sampler re-adds every previously stored job missing from the new listing and never expires them. While the condition lasts, no departure is detected: finished jobs stay RUNNING with frozen elapsed time, no finished event fires, history is never refreshed, and `t_jobs` makes the stale rows look fresh. ## Heavy allocations and the worker

Heavy's process hygiene is careful: the only scheduler mutation is a name- and uid-filtered `scancel`, signals go only to process groups Raven spawned, and receipts are published with no-follow, exclusive, fsynced writes. Its recovery, however, cannot recover. With the default empty `site.cluster_id`, any interrupted, rejected or crashed request blocks every later Heavy start for good — exactly the pair of errors the CARC launch showed — and Raven's own Cancel SIGKILLs `salloc`, so the queued request it means to withdraw survives and can later run unattended, billed, until its time limit. Reproductions used a fake `salloc`/`srun` that follows salloc(1)'s signal semantics and logs every signal, step exit and relinquish.

## Code that runs inside user jobs: metrics client, tracing and launch

This is the code with the highest bar — it runs inside other people's training and simulation jobs — and it fails that bar most often. The `@raven` client can hang a DDP job, leaks memory even outside Raven, and shadows other packages named `raven`; automatic tracing slows call-heavy Python by 65–431× and can block every new process in a project on one lock.

## Analysis, MCP and WASI

The sandboxes are the best-built code in the review — WASI and MCP contained everything thrown at them, and the Student-t, conformal and checkpoint math match SciPy to 1e-9 — but two research features return confident wrong answers on realistic inputs, and the expression language can still be driven to gigabytes.

**ANA-1 · High · VERIFIED (re-run independently) · `raven/experiment_design.py:96-146`, `:158-161`, `:186-194`.** The factorial model fits main effects, two-way interactions and blocks, and checks only that this reduced matrix has full rank. With three or more factors, if any planned cell has no supported observation (all repetitions excluded or never run), the omitted three- and four-way interaction columns alias onto the fitted ones and Raven reports confident, wrong contrasts. Blocked 2^3 design, 4 reps, `y = 10 + 1.5a + 0.9abc + noise(0.05)`, cell (+,+,+) excluded: state `observed-associations`, **a = +1.159 \[1.074, 1.243\] against a true +3.000**, and b, c, a:b, a:c, b:c all ≈ −1.80 with intervals excluding 0 against true 0. Without noise every contrast is wrong (state `zero-residual-variance`); with balanced data the three-way effect silently inflates the residual. The OLS arithmetic itself matches numpy and SciPy exactly. Fix: fit the full factorial when degrees of freedom allow; return "incomplete design" with no effects when any planned cell lacks a supported observation; if a reduced model is kept, run a lack-of-fit F-test against cell means and withhold intervals when it fails.

**ANA-2 · High · VERIFIED · `raven/phase_alignment.py:57-72`, `:104-118`.** Each feature is normalized by overall spread (max of the reference's MAD, span/6, 1% of the median), not by noise, so whether a phase change is found depends on unrelated larger changes elsewhere. DTW then aligns merged phases. Fix: normalize by robust noise (MAD of first differences / 0.6745 / √2), keep the median floor only as a minimum effect size, and return the most significant segments when the 32-segment cap is hit instead of raising.

**ANA-3 · High · VERIFIED · `raven/scientific_lineage.py:84-98`.** The greedy revalidation planner recomputes O(N) set differences for every remaining action on every iteration (O(A²·N) overall), takes no cancel, and in unmanaged mode runs in-process with no deadline. 4,000 changed artifacts: 256 actions 8.45 s, 512 actions 58.4 s, 1,024 actions did not finish in 280 s; the input limits allow 2,048. ## Installer and updates

## Structure and maintainability

The codebase grew by 18,000 lines in two days without changing shape: the same flat package, the same giant dispatch functions, and a dependency graph whose cycles are hidden inside function bodies. These are the conditions that produced most of the bugs in the sections above.

**S-1 · High · VERIFIED · whole package.** The import graph is acyclic only at module level. There are **1,968 function-level `import` statements in 229 files** (`controller.py` 163, `views.py` 141, `screen.py` 100, `cli.py` 75), and once those are counted, **168 of 332 modules form a single strongly connected component**. Consequences: a missing or broken import surfaces when a user clicks something, not at import time; per-call imports sit on hot paths (`views.py:2304` and `:2335` re-import `metadata_for_record` for every dependency row of every frame; `controller._handle` runs about 15 imports before it dispatches a key); and the core/lab split cannot happen — the project's own W42 record says the "core" prototype still has 310 modules. Fix: declare layers (terminal UI → application services → domain → adapters → transport), enforce them with the import-linter config that already exists but covers two paths, hoist imports to module level inside each layer, and break each cycle with an explicit interface or registry.

**S-2 · High · VERIFIED · `controller.py:660` (`_handle`, 406 lines, 201 branch nodes), `controller.py:1873` (`click`, 297), `controller.py:1522` (`run_command`, 262), `screen.py:889` (`_apply_input`, 293), `screen.py:242` (`_read`, 267).** Every keypress walks a hand-ordered chain of about 30 modal owners (history, terminal, column resize, queue drag, group drag, scrollbars, group menu, log export, data export, bindings editor, …), each behind its own import, and the first that claims the key wins. Ordering bugs between modes are the predictable result, and the earlier strategy's "one typed event router" (investment 03/08) is still unbuilt. Fix: a focus/modal stack where only the topmost owner receives input, and command dispatch driven by `command_registry` instead of `if/elif`.

**S-3 · Medium · VERIFIED · `MANIFEST.in`, `docs/implementation/`.** 22 MB of raw CI evidence is committed, including eight copies of a 530 KB `release-inventory.json`, and `MANIFEST.in` ships it (`recursive-include docs/implementation *.gz *.jsonl *.log …`). The sdist is **13.0 MB against a 1.9 MB wheel**, and every bootstrap install clones the full history (a 17 MiB pack) — the same clone that died in `git index-pack` on CARC. Fix: publish evidence as release assets or on a separate branch, exclude `docs/implementation` from the sdist, and clone with `--depth 1`.

**S-4 · Medium · VERIFIED · whole package.** 330 modules still sit in one flat namespace, with families standing in for packages (`raven_*` 19, `ops_*` 18, `terminal_*` 13, `job_*` 13, `series_*` 12, `launch_*` 11, `log_*` 10, `trace_*` 9). 116 functions exceed 100 lines and 15 exceed 200. 1,250 lines exceed 160 characters, and several modules (`raven_ui.py`, `raven_limits.py`) are written in a compressed one-line style that hides control flow from review. Rules that keep these from coming back:

1. A destructive command fails unless its target set is exactly what the user named.
2. Every budget degrades — drops the oldest, samples, or refuses one item — and is tested at its default value.
3. Every uncertain state has a path to certainty and a reviewed manual way out.
4. Nothing on the UI thread waits on a subprocess, an fsync, or a lock a worker holds.
5. Code inside user jobs decides from live runtime state, never blocks, and never kills.
6. A process is stopped the way its owner expects: hang up, wait, then kill the whole group.
7. Every fake reproduces the real tool's refusals, not only its successes.
