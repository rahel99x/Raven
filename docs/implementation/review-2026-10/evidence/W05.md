# W05 — Scoped mutable-state ownership

Source: A-08. Baseline: `33316a08bd583a242356c7722a21c10e00cff21b`.
Disposition: implemented for verified local Linux filesystems; distributed locking is explicitly unsupported.

The writer inventory distinguishes Store-owned tags, events, metric append files and `ui.json` from collection-ledger, project-evidence, runtime-mailbox and terminal services that already implement their own transactional/identity contracts. The missing protection was simultaneous independent Store writers reading the same mutable snapshots and replacing each other's state.

`state_ownership.StateOwner` holds a kernel flock descriptor for the exact state directory. Existing profile/host/user state namespaces remain the isolation boundary; this is not a machine-wide singleton. The lock file includes diagnostic host/PID/scope metadata, but metadata never establishes ownership and no PID is signalled. Crashes release the descriptor. Opening or unsupported locking errors are distinguished from an active writer. W04's pinned directory traversal rejects writable ancestors and symbolic-link substitutions before acquiring the file.

Interactive sessions request exclusive ownership and explain how to close the owner, select an independent namespace, or use `--no-state`. Headless readers and direct embedding clients fall back to read-only state when another writer owns the directory. An uncontended headless session retains its established ability to save collected data. An explicit `Store(..., read_only=True)` creates no directory or file. All Store mutation entry points check ownership, including append queues and UI preferences. Session cleanup releases ownership in a `finally` block even if another service fails during shutdown.

The simpler alternative, one global Raven lock, would block independent lab/profile sessions and headless exports. Independent locks for tags and UI would still permit stale read-modify-write snapshots from two processes. One descriptor per mutable scope is small and addresses the actual race without a daemon.

Only an explicit allowlist of local Linux filesystem types supports mutable state. NFS, Lustre, unknown filesystem types and unverifiable mounts retain read access but refuse a durability claim. `flock` on this host is not distributed-filesystem validation. For cluster use, select site-approved node-local persistent storage with `RAVEN_STATE_DIR`; retained scientific/project evidence can remain on the shared filesystem. A temporary runtime directory is suitable only if losing the local cache after logout/reboot is acceptable. No existing files are chmodded or relocated automatically.

Acceptance evidence in `tests/test_state_reliability.py` includes two actual processes, SIGKILL/reacquisition, a foreign-host stale PID, independent directory scopes, a read-only second writer, read-only nonexistent paths, permission/locking failures, unsafe symlinks/ancestors, network and unknown filesystem refusal, and exceptional Session cleanup. Existing desktop profile and CLI tests also exercise namespace separation.

Initial controlled open/close comparison: median 0.020462 → 0.158351 ms; p95 0.077328 → 0.224191 ms for 30 fresh local scopes. This is a deliberate ownership/mount/trust-check cost at startup, not a recurring scheduler query. The provisional p95 ceiling was 20 ms. Final source-frozen measurements remain a tranche gate.

Upgrade creates `.writer.lock` without changing existing data formats. Never delete a live lock file to bypass ownership: that permits a different inode to be locked concurrently. Closing the owner or choosing an isolated state scope is the recovery path. An old Raven binary does not honor this new lock, so mixed-version concurrent writers remain unsupported; close all instances before downgrade or upgrade.

## Platform compatibility limit

The final source review corrected an overbroad installation claim: filesystem verification currently reads Linux mount information. Persistent state therefore supports qualified Linux/WSL2 local filesystems; macOS persistent state is unsupported in this revision and ordinary interactive ownership can refuse it. `--no-state` avoids persistent mutation. This is a compatibility limitation, not macOS validation. A future Darwin filesystem implementation needs actual platform qualification before restoring the persistent-state claim. The final installation guide makes the boundary explicit.
