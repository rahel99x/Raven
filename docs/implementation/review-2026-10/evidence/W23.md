## Baseline and design

The baseline exported authoritative CSV/JSON evidence and had a bounded
expression evaluator, but no persistent relational evidence index. Reuse of
completed `data_export` inventories avoids a second live scheduler/recording
reader. A plain repeated CSV scan is simpler and remains appropriate for one-off
queries. SQLite adds build/storage cost in exchange for transactional ingestion,
provenance joins and indexed repeated selection; performance claims require the
equivalent-fixture measurements below.

Each immutable manifest is one transaction and ingestion checkpoint. A complete
attempt identity and exact source row bind observations; repeated capture
ingestion is idempotent. New captures remain distinct, even when their rows
repeat earlier evidence. Raw values, units, quality, missing reasons and all CSV
attributes remain available. Exact integers that cannot be represented by
binary64 have NULL numeric values with the original text and an explicit reason.
Attempts, log byte/line indexes and state evidence are also indexed. A final
state is a snapshot with an unknown transition timestamp, not an invented event.

The existing Operations workbench provides review → index/update → named views
or SQL → consistent SQLite backup. `ravenh query` shares its managed admission;
Light defers without reading evidence locally. Series transforms require one
capture/source/attempt/metric and one explicit rank/node/device stream. Rates,
counter deltas and observed-sample windows preserve gaps, resets, irregular
intervals and unavailable values. Existing expression syntax/budgets are
unchanged; no unproved SQL translation is introduced.

## Maintainer review and fixes

Independent review found that a VM-step limit alone did not bound allocation by
a short recursive string-doubling query. Per-connection SQLite value, statement,
column, expression and opcode limits now precede queries. CPython 3.10 uses a
disposable CPU/memory/time-bounded process because its sqlite3 lacks `setlimit`;
cancellation kills and reaps that child. The authorizer blocks writes, ATTACH,
PRAGMAs, extension loading and unapproved functions.

A second review found that a tampered existing index could make ingestion
evaluate a metadata view or execute an inserted trigger. Writers now verify the
complete expected table/index catalog before evaluating metadata or updating a
capture. Injected views/triggers are refused. Readers validate the exact ordinary
metadata table before evaluating bounded metadata rows. Project-scoped indexes
reject multi-project exports so raw manifest provenance cannot disclose another
project through a later scoped query interface. The expected project is checked
on the same database connection that executes the query, including the Python
3.10 child and MCP reader. A final independent review found no further substantive
issues in the repaired catalog/project binding seams.

Kernel-backed ownership serializes writers. Local-filesystem policy is explicit;
rollback journals and FULL synchronization avoid undocumented WAL/NFS assumptions.
SQLite's backup API produces consistent new-directory exports. Originals remain
authoritative and rebuilding is an explicit new-index operation.

A later independent review reproduced three additional fidelity gaps in CSV
ingestion. Decimal and exponent spellings of large integers bypassed the original
integer check; a different project could be silently omitted; and a multi-attempt
source could name another attempt from the same manifest. Ingestion now compares
finite decimal values without expanding huge exponents, retains unrepresentable
integers and underflow/overflow as text with NULL numeric values, and rejects
project or per-source attempt inconsistencies transactionally. Tests use complete,
checksum-consistent external CSV publications, preserve the previous committed
capture on failure, and exercise both SQL and series selection. The review and
its actual Python 3.10 child-cancellation observation are retained in
`W23-independent-slurm-review.json`; final focused evidence is separate from
the earlier 26-test result.

## Performance and limits

The final source-frozen rerun, including the numeric/source-identity corrections,
is in `W23-final-index-queries.json` and `W23-W28-final-cost-window.json`.
For 1,000/5,000 input records, the equivalent cached CSV selections took
9.064/45.601 ms and indexed selections 0.598/0.819 ms (15.2×/55.7× for this
fixture). Ingestion took 0.347/1.562 s. Fresh-child maximum RSS was separately
23.8/39.3 MiB. These are bounded selection results, not an end-to-end dashboard,
network filesystem or general database speedup. The previous run below remains
available with its original source hashes; differences between the two runs are
not attributed to the correctness fix.

The existing `benchmark_data_export.py` harness now supports `--index-queries`.
It uses the same independently verified export fixture for interleaved equivalent
CSV and indexed time-window queries, checks every result, and records ingestion
CPU/time, query plans, disk bytes, Python allocations and separate child RSS.
`W23-index-queries.json` preserves a controlled 20-repeat interleaved run, with
independent result equality and no competing heavy tasks. At 1,000/5,000 input
records (2,000/10,000 measurement rows), median CSV selection took 8.91/44.16 ms;
indexed selection took 0.62/0.72 ms (14.4×/61.6× faster for this cached fixture).
Ingestion took 0.35/1.53 s, with approximately equal CPU seconds. Python allocation
peaks during ingestion were 5.51/23.00 MB; query peaks were 16.3/16.4 KB versus
CSV's 46.7/46.8 KB. Fresh-child process maximum RSS was separately 25.4/39.4 MiB.
The indexes added 3.18/15.55 MB beside retained 0.73/3.65 MB raw exports. Query
plans use the measurement-window index with a temporary final-order term. This
is a repeated bounded-window benefit, not a free ingestion or disk-space gain.
The benchmark records exact indexer/exporter hashes. No scheduler commands run;
remote storage, cold-cache I/O, and managed large-index admission are not inferred.

Format ceilings are not new resource authority. The managed worker's smaller
source/output/CPU/memory limits still apply, and sources/indexes are charged
conservatively. Local SQLite/PTY tests are not remote-filesystem or deployed-site
qualification. Final integrated regression and packaging are still required.
