# W04 — Configuration and plugin trust

Source: A-08 and review A opening correctness concerns. Baseline:
`33316a08bd583a242356c7722a21c10e00cff21b`. Candidate: integration working tree;
[source hashes](https://github.com/rahel99x/Raven/blob/evidence/pre-review-2026-10-20/docs/implementation/review-2026-10/evidence/raw/W04-W07-source-hashes.json) identify the measured implementation.

## Verification and decision

Confirmed on the baseline: a mode `0666` legacy configuration was accepted and a
mode `0666` plugin executed its module body before any diagnostic. Managed config
already rejected a final symlink and oversized/nonregular input, but did not
verify ordinary file ownership, writable ancestors or in-place mutation. Setup
already used atomic saves and a lock; these mechanisms are retained.

[Actual before/after reproduction](https://github.com/rahel99x/Raven/blob/evidence/pre-review-2026-10-20/docs/implementation/review-2026-10/evidence/raw/W04-before-after.jsonl) uses a disposable
plugin that creates a marker. The candidate rejects both files with their path
and correction, and the marker is absent. Both runs use the same fixture.

The smallest shared mechanism is `config_trust.read`: walk directories through
pinned `openat` descriptors with `O_NOFOLLOW`, verify ownership/permissions, read
bounded regular-file bytes, then compare inode mutation metadata. Legacy and
managed loaders and Setup use it. Plugins compile these exact verified bytes;
`exec_module` would reopen the pathname or choose a bytecode cache after checking.
Runtime-control mailboxes reuse the same pinned private-directory integrity check while retaining their local-filesystem restriction. New mailbox creation validates its parent before writing. Config creation uses protected ancestors and mode `0600`; Setup preserves its
existing conflict token, lock, atomic replacement and durability warning.

A simpler `stat(path); open(path)` check was rejected because it leaves a path
replacement gap. Requiring every file to be `0600` would break harmless readable
site configuration. Integrity permits owned/root-owned `0644`; private files
require current-user ownership and no other access. Mandatory site policy also
requires administrator-owned ancestors. Arbitrary secret-bearing command text is
not inferably public/private: new configs are private, and the user guide explains
secret handling. Trusted Python remains unrestricted code.

## Acceptance and review

- Loader variants reject writable files/directories/ancestors, symlinks and FIFOs.
- Readable owned config and existing plugins continue working.
- A replaced ancestor cannot redirect the pinned read; a plugin path replaced
  after validation cannot substitute code for the verified source bytes.
- Setup refuses unsafe destinations; normal save/conflict/durability regressions
  remain covered. No implicit chmod/chown is performed.
- Private confidentiality and root-only policy checks are tested separately.
- Reviewer pass found creation through `os.makedirs` preceded validation; changed
  creation to descriptor-relative mkdir beneath already verified ancestors.

## Cost and limits

[Controlled interleaved measurements](https://github.com/rahel99x/Raven/blob/evidence/pre-review-2026-10-20/docs/implementation/review-2026-10/evidence/raw/W04-config-read.json): 30 warmups and
1,000 identical tiny JSON loads per fresh process, baseline/candidate twice.
Baseline mean 4.79–5.11 µs/read; candidate 40.30–42.96 µs/read. The additional
35–38 µs is a correctness cost on configuration loading, not a throughput gain.
Process CPU for 1,000 reads: 0.0051–0.0052 s → 0.0405–0.0431 s. Peak process RSS:
11,904–12,032 KiB → 12,032 KiB; this is OS RSS, not Python allocation tracking.

Work is O(path depth + file bytes), with constant descriptor count and bounded
reads (256 KiB config; 1 MiB plugin source). No polling, network request or scheduler
command was introduced. Group/world-readable files remain compatible; symlinked
or writable configuration must be corrected manually as described in the
[trust guide](../../../guides/configuration-trust.md). Rollback does not require a
format migration. A malicious same-user process or administrator is outside this
trusted-code boundary. Namespace-remapped filesystem owners are accepted only as
system ancestors, never as arbitrary user config/plugin owners.
