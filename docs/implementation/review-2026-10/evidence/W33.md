# W33 — Observable Slurm queue model

Source B-01. Baseline `33316a08bd583a242356c7722a21c10e00cff21b` had observational forecasts, but no discrete-event policy model. This package implements the handoff's staged **experimental** capability; it does not replace Slurm or certify an unobserved site.

## Model, workflow and alternatives

`slurm_simulator.py` models deterministic priority/resource/dependency scheduling, conservative EASY backfill, explicit exclusive reservation windows, bounded QOS running/CPU/wall limits and a documented decayed-account-usage fairshare subset. It preserves CPU/memory/GPU conservation and failed/timed-out afterok dependencies. Declared homogeneous per-node requests avoid guessing unsupported placement semantics. Hierarchical fairtree, arbitrary site priority, hidden demand, licenses, topology, federation, preemption and heterogeneous allocation remain explicitly unsupported.

Operations → Observable queue model exposes permitted configuration discovery and explicit-file simulation through the existing worker, cancellation, history and export boundaries. Discovery captures four bounded read-only commands, hashes evidence and preserves partial permission failures. It does not invent missing account policy or declare the resulting model complete. Managed simulations require Heavy; compute tasks cannot acquire scheduler discovery transport. Standalone explicit scenarios remain supported.

The simpler FIFO baseline is retained in tests and comparisons. Modelling all Slurm policies would add unqualified complexity; this explicit subset gives inspectable behavior and useful negative evidence. Simulations retain model version, input digest, parameters, origin, seed and operation counts. Caps cover nodes/jobs/traces, event count and placement work; cancellation is checked cooperatively. There is no mutation plan or automatic submission.

Calibration uses median runtime ratios from one set of distinct completed attempts. Validation uses a different, strictly later trace and reports start/wait MAE, tail error, coverage, ranking accuracy and hidden-state sensitivity. Training and testing cannot share attempt identities or overlapping chronology. Recorded and synthetic traces are labelled separately. Exact format and commands: `docs/guides/queue-model.md`, `examples/queue-model.json`.

## Independent real scheduler evidence

After hand-computable and invariant tests, the isolated real Slurm 26.05.5 W14 harness ran three calibration jobs followed by four later held-out jobs on its two-CPU/1 GiB node. This is actual controller, compute-daemon and accounting execution, without physical GPU or production-site claims. Known sleep commands supplied duration estimates before outcomes; observed release times supplied model arrivals. The predictor was not tuned on the holdout.

Command: `.venv/bin/python scripts/qualify_slurm.py --version 26.05.5 --skip-build --scenario queue-observations --output /tmp/raven-slurm-temporal-holdout-1`.

Preserved evidence: `measurements/queue-temporal-holdout/` contains the model, complete result, command capture, source provenance, image identity and package versions. Three calibration attempts yielded factor 1.0. Four held-out starts yielded **2.75 s start/wait MAE, 8 s p95 absolute start error, 100% prediction coverage, and 0.6 ordering accuracy over five non-tied pairs**. Immediate model backfill disagreed with actual short-job scheduling; the result is consistent with unmodelled scheduling-cycle timing and startup costs. It is not evidence of production fidelity. `production_qualified` remains false, and no holdout-driven parameter adjustment was made.

## Tests, review and limits

`tests/test_slurm_simulator.py` checks independent resource sweeps, hand-computed schedules, backfill reservations, QOS, failures, fairshare, temporal leakage, malformed/unsupported input, cancellation/budgets, read-only partial discovery, worker routing and exact replay of the negative real holdout. Review corrected runtime clipping so an over-limit modeled job cannot satisfy afterok dependencies. Combined checkpoint/campaign/queue/setup regression passed **121 tests in 0.77 s**; final revision validation is recorded by the parent ledger.

The implemented milestones and evaluation are complete. Wider deployment efficacy remains unproved: additional independently recorded site traces, supported-policy reconciliation and chronological holdouts are necessary before any production qualification. This model supplements real Slurm CI and cannot replace it.

Final focused integration: **945 tests passed in 29.70 s** across parser/accounting, managed collection, all four planning packages, existing launch/orchestration/worker paths and UI/setup. Exact command and source hashes: `slurm-planning-focused.json`; raw output: `slurm-planning-focused.log`. This complements, rather than replaces, the final integrated full regression.


The isolated controlled cost run (`measurements/planning-costs.json`) used the same 32-job fixture for FIFO and conservative backfill: **2.117 / 4.073 ms median CPU**, **37,528 / 37,582 bytes Python peak**, and **16,128 / 16,128 KiB process peak RSS**. The richer backfill policy costs about twice the CPU in this small fixture. It does not establish real scheduler throughput or fidelity. The serialized quiet window ran on 2026-10-18 from 00:33:01.675 to 00:33:13.320 UTC; source hashes and raw samples are retained. CPU uses process time; RSS includes imports and fixture construction and is distinct from Python allocation peaks. No scheduler or network I/O occurred.


After the final safety guards, **191 algorithm/control tests passed in 3.12 s** and **410 existing planning, launch, UI, Setup and campaign integration tests passed in 5.85 s**. Exact commands and changed-source hashes are retained in `planning-final-focused.json`; the parent ledger supplies full delivered-revision gates.
