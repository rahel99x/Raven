# W17 — Ownership-preserving allocation recovery

Source: A-11. Baseline: `33316a08bd583a242356c7722a21c10e00cff21b`.
Disposition: implemented with explicit scheduler qualification gates; unknown ownership remains blocked.

The baseline correctly kept Light usable after losing a worker, but an uncertain receipt permanently blocked another allocation without a reconciliation procedure. It also lacked a unique scheduler name that could authorize a safe orphan cancellation. Reading an owner and subsequently issuing `scancel JOBID` would introduce a recycled-ID race.

Dedicated Raven allocations now receive an exact `raven-heavy-<128-bit request token>` job name. The helper persists the name, connection binding, request creation time, reviewed cleanup intent, helper host/boot identity and existing allocation evidence before launch. Request names are added to the actual dedicated `salloc` argv; reused scientific allocations are unaffected. Receipts retain their existing v1 schema and scope path. File and directory fsync, atomic replacement, private ownership checks and a pinned directory descriptor protect publication. Unknown/missing receipt schemas remain unchanged and cannot authorize an action.

A finite task on the existing verification executor reconciles a prior receipt. Its exclusive kernel lock must be available: recorded PIDs, including foreign-host PIDs, are never used as authority or signalled. Connection, actual controller cluster, current account UID and exact request name are checked. A pending request lost before its job ID was observed can be located by its unique name. Every accounting lookup specifies a bounded time window, user and duplicate records; the W03 window helper is reused. Empty, delayed, malformed or inaccessible accounting remains unknown.

Active orphan cancellation uses one controller RPC with all three constraints: `scancel --ctld --name=<exact token> --user=<verified UID> JOBID`. Both client and actual controller versions must be explicitly qualified. There is no bare-ID or per-step fallback after failure. A successful cancellation response does not clear uncertainty; a later exact terminal controller/accounting record does. Terminal records from the original request can establish cleanup after the numeric ID is reused, without cancelling its new owner.

Automatic recovery has eight attempts per persisted cycle, exponential delays beginning at five seconds, bounded jitter and a 300-second base cap. Reservation is persisted before scheduler access, so a crash consumes its attempt. Admission deferral preserves its retry hint. Errors, attempt count, next retry and next action appear in allocation inspection. Exhaustion pauses the cycle. **Retry cleanup** starts another bounded cycle after the existing confirmation flow; it neither requests Heavy nor resubmits a scientific job. Missing or unsupported receipts pause with a recovery explanation. Local lock/access failures have a separate bounded in-session retry policy because overwriting unreadable or actively owned state would be unsafe.

The simpler alternative is to retain manual-only cleanup. It is safe but leaves an ordinary transport failure unresolved. A persistent daemon is unnecessary: the existing manager, receipt lock and finite verification executor provide the required lifecycle. The alternative read/check/bare-cancel sequence is rejected because it cannot close the scheduler TOCTOU race.

Review findings resolved:

- The W16 contract review identified unsupported receipt-schema reinterpretation; reads and writes now reject it, preserving bytes and making zero scheduler calls.
- A missing receipt initially caused repeated background filesystem checks. It now pauses immediately without claiming cleanup.
- Ownership-directory checks initially ended before publication. The validated directory descriptor now remains pinned across lock, read, replace, unlink and fsync.
- Atomic cancellation qualification checks the controller's `SLURM_VERSION` from `scontrol show config`; a client `scontrol --version` is insufficient.

Validation uses `tests/test_allocation_recovery.py` plus existing allocation, UI and W16 stateful ownership/fault suites. The latest combined run passed 135 tests; four additional targeted crash/reservation, disk-full, permission and read/cancel crossing tests subsequently passed in the 28-test recovery module. Existing assertions that uncertainty blocks new allocations remain; UI tests additionally verify reviewed cleanup sends no scientific-job action and does not clear uncertainty on its own. The retained `W17-live-manifest.json` records source hashes, its baseline revision and actual results; `W17-live-commands.json` preserves commands. This one-container qualification is not production-cluster or arbitrary-version qualification.

Remaining deployment limits are explicit. An active legacy receipt without a unique token cannot be cancelled automatically; exact terminal identity may still clear it. An active reused parent is never cancelled to clean its worker step; terminal parent evidence can clear it, otherwise site-qualified exact-step ownership is required. A local worker without a provable live process lifetime is not killed from a saved PID. Unknown versions, modified vendor semantics, missing original receipts and unavailable scheduler permission require restoring/verifying that dependency before automatic cleanup can proceed. None of these conditions is bypassed by a timeout.

Performance fixture: `scripts/benchmark_allocation_recovery.py` measures 30,000 identical idle manager ticks, reporting microseconds, CPU time, process RSS and separate Python allocations. Its baseline/current runs must be serialized with other benchmarks. Recovery commands are bounded and only emitted while reconciliation is needed; an idle manager submits none. These are reliability costs, not a performance improvement. Raw results: `recovery-before.json` and `recovery-after.json`. Final integrated revision checks remain a release gate.

Upgrade requires no receipt deletion or manual migration. Keep the existing state directory on node-local storage, stop old Raven processes, install the revision, then open allocation inspection. Retain any uncertain receipt; deleting it discards the evidence required for safe recovery. An unsupported receipt schema must be read with its compatible version. No automatic downgrade conversion is performed.
