## Design and complete path

`campaign_policy.py` requires the unchanged scoped orchestrator review. Modeled jobs, dependencies, account/QOS, CPU/node/GPU/memory/wall resources must match that review exactly. Optional execution receipts retain their original identities; accepted nodes never become new candidates and uncertain/rejected outcomes require the existing reconciliation workflow. The original files and receipts are never rewritten by comparison.

The existing execution workspace exports `execution policy QUEUE_MODEL.json LIMITS.json OUTPUT.json`, capturing the current review/receipt and refusing overwrite. Operations → Campaign submission policy performs comparison through Heavy in managed installations. Pause/resume/cancel/override are separately reviewed interface-owned local controls, scoped by connection and immutable review ID. They use the existing durable action lifecycle, atomic state and revision checks. A changed input, connection or control requires a fresh review; local cancellation requires a new immutable review before continuation. Compute tasks cannot acquire local control ownership.

FIFO, submit-all, shortest, backfill-friendly and fairshare heuristics use the same declared workload and limits. Admission conservatively counts all outstanding requests against concurrency, MaxSubmitJobs, group CPU/memory/GPU limits and external usage; command spacing is bounded. This intentionally stricter envelope can reduce utilization relative to Slurm's later allocation checks, and is disclosed. Afterok failures block descendants. A starvation threshold restores older-work precedence; fairshare timing is a bounded heuristic, not Slurm hierarchical fair-tree.

A simpler static job sort would miss outstanding resources, dependencies and command load. A new autonomous scheduler would duplicate unsafe ownership/recovery code and exceed the initial qualified milestone. The selected design produces reviewable shadow decisions and preserves explicit scientific execution in the established workflow. It cannot automatically enforce future policy timing on that executor, and does not claim to do so.

Comparisons report makespan, throughput, wait tails, starvation, modeled wasted CPU time, command counts/rate, coverage and signed gains/regressions versus FIFO. Runtime factors 0.5 and 2 expose forecast-error sensitivity; over-limit modeled jobs cannot satisfy afterok. A single combined one-million-placement budget covers all five policies and sensitivity runs, with cooperative cancellation and a 64-node inventory bound.

## Final Python 3.10 compatibility correction

The complete Python 3.10 run found eight campaign-analysis failures because `math.exp2` requires Python 3.11. Replacing it with `math.pow(2.0, exponent)` preserves the validated nonpositive decay domain and supports the declared minimum interpreter. Independent review checked underflow and ordering semantics; last-bit libm differences are not represented as bitwise equality. The existing 17 campaign tests passed on Python 3.10 and 3.12. [The correction receipt](https://github.com/rahel99x/Raven/blob/evidence/pre-review-2026-10-20/docs/implementation/review-2026-10/evidence/W35-python310-compatibility.json) records the failed baseline and focused commands; final integration evidence separately names the delivered revision.


## Python 3.10 compatibility correction and final cost refresh

The final interpreter matrix exposed use of `math.exp2`, introduced in Python
3.11. Revision `0d138fdacbcfb2d58c3d77a0494d439c7d2204e8` replaces this call with
`math.pow(2.0, exponent)`. The validated decay exponent is nonpositive, so both
forms retain the same bounded exponential-decay interpretation; ordinary libm
last-bit differences remain possible. The initial failed matrix remains part of
the release evidence. The owning integrator reports all **17 campaign tests
passing on both Python 3.10 and 3.12** after this correction.

The existing harness then reran its unchanged 32-job fixture in an exclusive
2.33-second slot. FIFO median CPU was **6.793 ms**, versus **6.204 ms** previously
(+9.48%). The complete comparison was **104.497 ms**, versus **105.346 ms**
(−0.81%). Python allocation peaks remained **79,216 / 254,098 bytes** and separate
process RSS **16,256 / 16,896 KiB**, respectively. Full comparison performed the
same **23,760 placement operations**. The unchanged FIFO path also varied, so
these observations are not a causal speedup claim for the one-call correction.

`../measurements/planning-campaign-final-0d138fd.json` retains exact commands,
raw five-sample CPU arrays after two warmups, separate allocation/RSS values,
UTC bounds, the fixture/source hashes and original baseline reference. The
revision-wide final regression remains the parent ledger's release gate.
