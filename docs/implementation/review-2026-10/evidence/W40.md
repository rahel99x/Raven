# W40 — Optional pure-analysis WASI boundary

Source A-12; baseline `33316a08bd583a242356c7722a21c10e00cff21b` has trusted
Python plugins and reviewed subprocess adapters, not a WASI runtime. This package
adds a compatible pure-analysis milestone; it does not claim arbitrary Python,
native, MPI or CUDA programs can migrate unchanged.

## Design and tradeoffs

The optional dependency is the actual installed and tested `wasmtime==49.0.0`.
The restricted `raven.f64-summary/wasi-preview1-v1` ABI takes a bounded finite f64
series and returns count, sequential sum and extrema. A supplied WAT example can
be compiled using that runtime. Trusted Python remains a distinct execution path.

A simpler alternative is the existing trusted Python summary: less startup cost,
less code and ordinary filesystem/process authority. A general WASI context would
improve adapter compatibility but expose more host APIs and more blocking-I/O
semantics. The chosen small import allowlist supplies only bounded in-memory
stdin/stdout/stderr and process exit; no path, preopen, environment, network,
clock or randomness capability exists. Unsupported imports fail before startup.
This intentionally trades compatibility and per-call overhead for a smaller
explicit authority boundary.

The runtime, Python runner and host kernel remain trusted. The boundary does not
claim immunity from implementation vulnerabilities, side channels or denial of
service. An arbitrary adapter may produce false scientific results. Result
receipts bind reviewed module/input/output digests and limits; they do not certify
scientific validity or universal numerical determinism.

## Complete workflow and recovery

The existing operation palette exposes `wasi-analysis`, without a new permanent
view. Inspect hashes the module/input and displays runtime, ABI and explicit
limits without executing guest code. Run prepares a plan; keyboard-visible
Review/Apply is required before execution. Apply rereads exact bytes, checks the
same runtime/module/input/limits and verified worker identity, then executes the
bounded child. Optional publication uses existing no-clobber receipt semantics.
Changed sources require a new review; cancellation/failure does not publish a
successful result; completed receipts are reconciled before another explicit run.

Managed Light defers. Managed Heavy uses the named `wasi-analysis-execute` adapter,
existing verified worker placement, resource admission and mutation uncertainty
handling. Arbitrary local fallback and automatic mutation replay remain disabled.
The runner stays in the owned worker process group and cannot spawn children.
The default installation does not require Wasmtime; missing or mismatched runtime
versions produce an actionable diagnostic.

Guest memory, table count/size, instances, stack, fuel and output have hard runtime
bounds. The whole runner has a separate address-space/CPU/descriptor cap. Module
compilation and execution count against parent wall time. The parent independently
streams and caps stdout/stderr and kills its exact child on timeout/cancellation.
Fuel does not bound host I/O: supplied host calls perform only bounded in-memory
copies and never block on external I/O. Host pointer/iovec checks prevent reads or
writes outside guest memory.

## Tests and skeptical review

Actual Wasmtime tests cover the example against the trusted sequential reference,
negative/fractional/cancellation-prone values, repeated extrema and signed zero;
real imports attempting paths, symlinks, environment, sockets, clocks and entropy;
memory/fuel/output exhaustion; malformed host pointers; independent wall-time and
cancellation; parent output limits independent of the SDK; changed source/refused
publication; runtime absence/version mismatch; schema authority rejection;
80-column palette Review/Apply; and actual owned WorkerClient execution/persistence.

The first fidelity run found `f64.min/max` chooses signed zero differently from
Python's first-value tie rule. The example now uses explicit strict comparisons;
behavioral byte-digest assertions were retained. Runner process ownership was
reviewed and a detached subprocess group was removed so outer worker termination
also covers the runtime. Inherited hard limits are capped rather than raised, including a 30-second request
inside an actual worker with a 30-second hard CPU ceiling. Huge integer inputs
produce a bounded f64 diagnostic. Independent root review found integer-to-f64 precision loss. Nonexact integers
are now refused before packing; exact large integers such as `2**60` remain
supported, with positive and negative regression cases. Preview metadata calls its list `allowed_imports`, rather
than falsely presenting it as the supplied module's actual import declaration.

After disk recovery, combined WASI, session/shared service, signing and execution
checks passed: **208 passed in 6.69 seconds**, including the 80-column visible
review and schema checks. After the final inherited-limit and peer-fairness
adjustments, **80 service/WASI tests passed in 4.67 seconds**. Interrupted full-disk
results were discarded. Independent maintainer review findings were resolved. Final integrated revision
validation remains pending. The subsequent six-package focused suite passed
178 tests in 6.26 seconds, including all 34 WASI checks.

[Controlled cost fixture](https://github.com/rahel99x/Raven/blob/evidence/pre-review-2026-10-20/docs/implementation/review-2026-10/evidence/raw/W39-W40-cost.json): ten runs of the same ordered
10,000-value series took 0.00294 seconds in trusted Python and 0.49279 seconds
through the WASI boundary, approximately **49 ms added per invocation**. Both
returned identical count/sum/extrema. Trusted parent CPU was 0.00294 seconds;
WASI parent CPU was 0.03640 seconds plus 0.45719 seconds in joined children. Each
parent's OS maximum RSS was 19,620 KiB in this harness; the maximum individual
runtime child was 26,872 KiB. These are process high-water values, not Python
allocations or simultaneously sampled process-tree RSS. No aggregate memory or
scientific performance improvement is claimed.

The WAT fixture is compiled once in the driver before isolated measurement;
the trusted child never imports the runtime SDK merely to prepare an unused
module. Every actual WASI invocation includes its bounded runtime child startup,
compilation, execution and validation. This small adapter is substantially more
expensive than trusted Python; that cost buys a narrower authority boundary, not
faster numerical analysis. The single controlled local run does not establish
production cluster latency or a universal overhead distribution.

**36 passed in 2.92 seconds** after the correction.

## Documentation and qualification limits

`docs/guides/wasi-analysis.md` includes installation, a complete compilable example,
exact binary/JSON formats, limits, review/recovery, threat model and runtime update
policy. The strict manifest schema ships alongside the guide. Runtime advisories
must be reviewed before changing the pin; hostile/fidelity/worker/resource checks
must pass again. Production cluster deployment, arbitrary WASI compatibility,
external security audit and runtime-vulnerability freedom are not established.
