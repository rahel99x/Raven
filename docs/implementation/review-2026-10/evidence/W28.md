## Baseline, design and compatibility

The existing command replay selected the first answer even when its completion
lay in the future. Recordings also timestamped request start, so delayed responses
could appear available too early. New recordings separate request and observation
completion; replay now refuses unavailable earlier answers. Legacy timestamps are
visibly labelled reconstructed rather than silently promoted to known-at-time.

Reconstructing all historical state from today's accounting rows would be simpler
than recording observations, but cannot establish what Raven knew earlier. The
new opt-in timeline instead captures only bounded published Store data, reusing
Jobs/History/transitions and exact attempt-scoped selected telemetry. It makes no
new scheduler or archive reads. Snapshot completion and source time are distinct;
late data appears only in later observations. Retention is64frames/7MiB, each frame
at most2MiB with explicit row/sample omissions and unknown intervals.

A dedicated existing-workbench inspection mode provides Jobs, History, Analytics,
Previous/Next, Diff and Live controls, plus UTC/epoch command navigation. It is
reachable from Run home and preserves that run binding. Navigation context is
labelled separately from snapshot telemetry; job-number coincidence is not proof
of scientific-attempt identity. CPU/memory render independently of GPU. Existing
charts draw observed bars without joining unknown intervals. Exact source values
remain available after charts and in explicit atomic new-directory archives.

Immutable encoded frames plus a bounded metadata clone are simpler than a new
mutable time-index database at this scale. All validation, decoding, comparison,
and chart preparation use the existing bounded worker lane. Paint only slices
prepared rows. Recording is off by default and never grows disk automatically.
No new global bracket shortcuts conflict with log/terminal navigation: all new
keys belong to the exclusive historical mode.

## Skeptical review

Independent reviews identified and resolved: future-answer leakage; UI-thread
snapshot parsing and repeated full rendering; quadratic identity-set construction
under Store.lock; same-second requeue restoration/diff identity; conflicting
selected/inventory/source-scope identity in imports; duplicate ambiguous rows;
extreme calendar clocks; stale asynchronous view publication; and hidden live
rows or click targets around a modal border. Reviews of the repaired controller
key/mouse/action guards, prepared publication and source/clock consistency found
no further substantive issues. Source hashes and focused commands are recorded
in `W28-focused.json`.

## Validation and remaining evidence

The188-test focused integration passed in6.71s on CPython3.12.14. New tests cover
late arrivals, immutable reads, exact same-second requeues, duplicate identities,
timezone equivalence, backward clocks/source epochs, partial retention, checksum

actual Workbench commands, keyboard and pointer action exclusion, preservation of
live scroll/selection and Run home binding, stale view results, legacy labels,
and CPU/memory when GPU is absent. Existing replay/source/run-home/quiet-frame

Later report integration exposed identity-only equality in the retained Timeline
container. It now has value equality and reports clone its bounded metadata,
preserving the existing deep-copy/no-UI-mutation assertion. A captured live report
also clears a historical overlay only on its private copy, so it cannot produce
blank pages or alter the user's historical mode. Fifty focused historical,
report, background-export and isolated SSH helper checks passed in 1.14 s after
this correction. These subsequent changes do not alter the measured seek/layout
paths; their exact hashes are recorded separately in `W28-report-integration.json`.

`scripts/benchmark_historical.py` reuses the checkout-verifying benchmark loader
and measures snapshot preparation, bounded metadata cloning, seek, Jobs/Analytics
preparation, diff, exact archive bytes, Python allocations and separate process
RSS. The exclusive run on 2026-10-18 used 32 frames, 200 samples per frame, and
100 or 1,000 jobs, with 20 repetitions per operation. Median seek was 1.871 or
10.132 ms; Jobs preparation was 1.850 or 10.618 ms, Analytics preparation was
3.495 or 11.277 ms, and diff preparation was 4.381 or 24.445 ms. The UI metadata
clone remained about 0.004 ms at both sizes. Snapshot encoding and validation
cost 1.995 or 10.724 ms; this uses an already constructed plain-data fixture and
does **not** measure the Store-lock copy. No new-capability speedup is claimed
against an imaginary predecessor.

At 1,000 jobs, seek and diff peaked at 987,637 and 2,072,347 bytes of Python
allocations respectively; the fresh process peaked at 59,924 KiB RSS. These are
different measurements. Its 32-frame archive occupied 4,416,968 bytes, including
6,856 bytes of metadata. The benchmark issues no scheduler commands. Exact
source and fixture hashes, timings, CPU measurements, allocation peaks and disk
sizes are retained in `W28-measurements-100.json` and
`W28-measurements-1000.json`; `W28-window.json` records the quiet-window commands
and successful completion.

Final full regression, clean-wheel entrypoints, compatibility and installed helper
checks apply to the eventual integrated revision. Snapshot checksums establish
consistency, not independently verified producer truth or a complete scheduler
