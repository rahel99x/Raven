## Implementation and tradeoff

Each command independently probes `--help`; supported JSON is normalized only
when its declared data-parser schema is qualified. Results are cached for one
hour and explicitly invalidated by manual refresh. `data_parser/v0.0.45` is
qualified against actual Slurm 26.05.5 output. Other schemas use a visible,
established legacy fallback. Malformed JSON, duplicate keys, invalid required
fields and transient command failures cannot silently become legacy success.
Unknown descriptive extensions are tolerated. Missing counters stay unknown.

Queue, account queue, current details, bulk accounting, historical log paths,
submission metadata and completed steps share this boundary. Targeted accounting
uses typed values directly, preserving literal pipe characters and UTC-aware
identities. All paths retain existing scheduler admission, response-size and
per-attempt history bounds. Help adds one cached command per tool; a newly
discovered unsupported schema can add one unsuccessful structured read before
fallback, recorded in accounting diagnostics. No slurmrestd is required.

A simpler version-number switch would be cheaper but cannot distinguish a
missing JSON plugin or a different data-parser schema. A universal permissive
JSON mapping would conceal semantic changes. The chosen adapter is deliberately
small and explicit; unqualified schemas keep the existing checked reader.

Record/replay wrappers preserve the underlying capability contract. Replay
probes only help actually captured for that command. Older recordings remain
compatible, and a recorded current-format error still takes precedence over
legacy aliases. Sources displays reader choice, reason, accounting window and
in-memory SSH connection notes. See `docs/guides/slurm-readers.md` for user-facing
controls, bounded historical lookup and compatibility options.

## Verification and review

`tests/test_slurm_json.py` compares every stable shared queue/accounting field
with the real legacy corpus: names with spaces/assignments, requested resources,
account/QOS, arrays, paths, times, CPU/RSS and duplicate requeue identities. It
also covers capability cache/invalidation, unsupported schema, malformed JSON,
transient errors, unknown extensions, absent required values, literal delimiters,
suspension runtime and new/old recordings. W02 adds Hypothesis parser properties.

The focused integrated sweep passed **566 tests in 22.40 s**; exact command and
source hashes are in `W15-focused.json`. W14 separately exercised Raven's actual
`jobs`, `details` and `finished` methods against the running 26.05.5 controller,
compute daemon and accounting database, with all three readers reporting JSON.
This is real single-node container qualification. It is not a production-cluster,
remote-site or physical-GPU claim.

Skeptical review found and corrected: capability wrapper leakage into legacy
fixtures; replay probing absent historical commands; loss of pipe characters
when structured rows were initially joined back into text; naive/aware identity
mismatches; incorrect assumption that step submission equals parent submission;
stale completed-detail caches and in-flight identity changes. Recorded Slurm
source confirms suspended runtime semantics; stale `last_update` is not used
as the live clock.

## Measurement and remaining limits

`scripts/benchmark_slurm_readers.py` repeats 500 real recorded pending-job
records with distinct IDs. It measures identical stable facts in separate
processes, including JSON decode/validation, seven CPU samples after warmup,
Python allocations and independent process RSS. Raw results are kept under
`measurements/`; they quantify overhead rather than claim JSON is faster.
Actual scheduler database load/latency remains workload-dependent. Historical
Slurm versions fall back until their exact schema has independent corpus
evidence. The W14 matrix and final integrated ledger record those results.

The serialized optimized measurement (same 500-record fixture) records JSON
median CPU **86.50/90.25 ms**, down from the first implementation's
**180.99/192.54 ms**, after removing repeated Python per-character validation
while retaining bounds, duplicate checks and strict semantic parsing. Legacy
medians were **3.10/3.03 ms**. JSON still costs approximately 29 times the parser
CPU for this fixture: the complete structured response is 2,901,426 bytes versus
111,391 bytes for the selected legacy fields. JSON peak Python allocations were
about **8.40 MB** and process RSS **44.3 MiB**, versus **0.77 MB** and **25.1 MiB**.
These are explicit regressions relative to selective legacy output, traded for
unambiguous typed values and supported-schema diagnostics. The bounded reader
and `RAVEN_SLURM_FORMAT=legacy` compatibility option remain available; none of
these CPU measurements include live scheduler or network latency. Raw repeats
are `measurements/json-legacy-readers-optimized.json`.

Final focused integration: **945 tests passed in 29.70 s** across parser/accounting, managed collection, all four planning packages, existing launch/orchestration/worker paths and UI/setup. Exact command and source hashes: `slurm-planning-focused.json`; raw output: `slurm-planning-focused.log`. This complements, rather than replaces, the final integrated full regression.


The final historical matrix reproduced a capability-discovery defect against actual Slurm 23.02.8: its valid JSON uses `meta.plugins.data_parser`, whereas 26.05 uses `meta.plugin.data_parser`. The reader now recognizes both exclusive metadata spellings solely to identify capability; recorded `data_parser/v0.0.39` remains explicitly unqualified and takes visible legacy fallback. Missing, conflicting or malformed identities still fail without fallback. The exact captured response and provenance are retained under `tests/fixtures/slurm/recorded/23.02.8/`; the JSON regression suite passed **26 tests in 0.22 s**. The failed real run remains in the durable qualification output rather than being relabelled successful.


## Final real scheduler compatibility matrix

The final isolated controller, compute and accounting lifecycle passed on **Slurm
23.02.8, 23.11.11, 24.05.8, 24.11.7 and 26.05.5**. These runs exercised actual
Raven readers alongside pending/running/completed states, arrays, cancellation,
requeue, controller reconnect and genuine numeric job-ID reuse with retained
accounting. Older structured schemas retain explicit legacy fallback; the
qualified 26.05.5 schema uses JSON. Historical missing output-path fields remain
unavailable rather than fabricated.

[W14-reader-matrix.json](https://github.com/rahel99x/Raven/blob/evidence/pre-review-2026-10-20/docs/implementation/review-2026-10/evidence/W14-reader-matrix.json) records each exact command,
start/end time, source hash and image ID. The corresponding complete captured
outputs and manifests are under `tests/fixtures/slurm/recorded/<version>/final/`.
These final runs include W06's qualified retained restart identity. Each reused
an exact-version compiled image and package snapshot with the current read-only
entrypoint supplied at runtime; they are **not clean rebuilds from the current
Debian-snapshot Dockerfile**. Physical GPU, multiple-node and production-site
qualification remain outside this evidence. Earlier failed runs are preserved
as issue baselines and are not counted as successful qualification.
